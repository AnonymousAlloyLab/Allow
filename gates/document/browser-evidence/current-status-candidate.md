# Document browser acceptance: candidate status

This is a draft inventory, not an acceptance report. `docs/document-stage.md` predates the connected browser evidence: its statement that no browser surface was available should be updated only when the evidence is reconciled. Existing observations are partial and include a known failure; the pointer-drag attempt did not produce an observable drop. The 500-node warm preview baseline reports p95 12.3 ms before the partial-types fix, using real controller edits and two animation callbacks; it does not establish physical paint, post-fix performance, server diagnostics, or accessibility. The reported 164 frontend tests and build/style checks are implementation evidence, not manual browser acceptance.

## Remaining finite scenarios for the available Chrome 156 in-app browser

Record actual browser version, setup, each action, visible and accessible outcome, failures and evidence. Use an isolated test document and preserve accepted and draft identities where relevant.

1. Reproduce the fixed `some Person` → Not insertion rejection with keyboard and pointer, then permit a compatible relation insertion and completion; verify unchanged state on rejection, visible reason, focus, Save state, and persisted accepted source. Repeat the pointer drag attempt with observable drag/drop events; absence of a drop remains incomplete, not a pass or proof of a product failure.
2. Keyboard-only create signatures, field, predicate and parameters; exercise all 23 expression tags across operator families, fill typed slots, inspect visible constraints, and cover compatible and incompatible cases. Exercise Tab/Shift+Tab, Enter/Space, Escape, focus after success/delete/rejection, associated errors and polite announcements. Check shortcuts and native text editing/selection/undo are not intercepted.
3. Move and copy a quantified subtree by keyboard and, if supported by the available surface, pointer: check preserved IDs on move, fresh expression/binder IDs and capture avoidance on copy, and rejection of escaping variables. Check rejected drop leaves selection, clipboard, focus, draft and accepted state unchanged. Exercise delete, Cut/Copy/Paste and Undo/Redo.
4. Save and inspect revision authority versus draft; exercise concurrent stale edit, lost acknowledgement and exact retry, and restart/recovery with preserved draft where the required controlled failure setup is available. Report each unavailable fault injection as incomplete.
5. Exercise repeated references, non-BMP and CRLF source navigation, and delayed validation after selection or edit; verify current focus and evidence do not move to stale results. Exercise comment copy/move/delete and orphan notices; verify history undo/redo creates new revisions while retaining historical source. Switch TEXT_ONLY to supported source and back, and verify invalid drafts leave accepted content visible.
6. Run automated accessibility scanning when the tool is available, recording tool/version and results; it supplements manual scenarios and does not establish WCAG compliance.
7. Complete the approved post-fix actual-browser 500-node series: 100 warmups and 1,000 ordered measured edits, full samples and p50/p95/p99, identity and DOM checks, environment and interruptions. Preserve the pre-fix baseline separately. Run and report a separate cold-start series. Measure authoritative diagnostics separately from API send through validated response processing, including network and worker startup, against the unchanged p95 <300 ms target. Missing or invalid series remain incomplete and failures remain explicit.
