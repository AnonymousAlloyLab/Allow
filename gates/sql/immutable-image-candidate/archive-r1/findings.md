# Candidate findings

The sealed-image design is locally viable as a candidate. An isolated probe copied the136492600-byte pinned ELF into memfd, applied all four required seals (mask15), hashed the sealed destination to9b252aabef502a9471f64c60ad2b0821e9db209a275c7ba8a4bd01da275e0cf7, and received EPERM on attempted write/shrink/grow. One exact SELECT1 request executed the parser through /usr/bin/prlimit and inherited /proc/self/fd/N successfully in0.0200seconds in the updated process-identity witness. This is one capability observation, not a benchmark or production result; no database connection was made. See probe-result.json.

The current guard hashes the live disk executable before every cache lookup, again after acquiring a parser slot on misses, and again before cache insertion. Sealed image checks can replace131MiB hashing on cache hits with bounded syscalls conditional on explicit fd ownership and kernel trust. The existing check also has a pathname re-resolution interval between hash and exec; executing the pinned sealed fd removes that interval for executable bytes. No production implementation has been changed.

The design changes disk-tamper semantics and must receive explicit review as a contract revision. It cannot both eliminate disk byte reading and claim to detect arbitrary disk byte changes at every admission. Retaining a known-good immutable running image is a distinct policy. Kernel/loader/shared-library trust remains. Parent/system memory increases by roughly130.17MiB backing storage for the image; child1GiB AS is not an aggregate bound.

The shell-default Python3.10.11 has no os.memfd_create; /usr/bin/python3 and .tools/retrieval-venv/bin/python are3.12.3 and provide it. Capability must be checked in the actual service interpreter. The kernel currently reports vm.memfd_noexec=0. Stronger host policies may deny executable memfd and must fail closed.
