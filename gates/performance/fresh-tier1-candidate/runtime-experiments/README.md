# Fresh Tier1 copied-stack harness

This directory is an authored gate, not a production launcher. It does not select F1 or establish target-host acceptance. The approved contract and experiment in the parent directory remain authoritative. All run metadata and diagnostics are private; no bearer URL is printed. Logical run directories are under `runs/`; physical copies use unique mode-0700 `/tmp/allow-ft1-*` roots so PostgreSQL Unix socket paths fit the kernel limit.

`controller.py prepare --run-id NAME --source-ready RECEIPT.json` copies source/configuration, the explicitly supplied compiled backend target, PostgreSQL executable prefix, parser and pinned source archives. It admits no existing `.runtime`. It pins the managed Python environment alias, existing bytecode and standard library, exact external tree members and link states, JDK including modules/CDS/native files, launcher binaries and their native dependencies. Every copied regular file receives an independent inode. Preparation creates no service or SQL connection.

The source-ready receipt has `status: SOURCE_READY`, `files: [{path, sha256}]`, and `backend_target: {path, files: [{path, sha256}]}`. Source paths are repository-relative; the target path is absolute and target file paths are target-relative. The source inventory must cover every non-cache file in `retrieval`, `scripts`, `config`, `db`, `spec`, `backend/src`, plus `backend/pom.xml` and `gates/document/headless-preview-fixture.json`. The compiled inventory must exactly cover target `classes`, `dependency` and `solver`. Optional `probe_classes` must contain exactly the two SHA-bound `dev/allow/backend/FreshTier1ProbeMain[\$Options].class` paths from target `test-classes`; these are copied to `.gate/probe-classes` rather than admitting a broad test classpath.

`installation.verify(manifest, fresh=True)` rejects mutations, unknown copied input files, changed external tools/aliases and live runtime state. `installation.finalize(manifest, root, variant, run_id)` returns an updated manifest without writing it. The caller must separately establish an allowed source/bytecode delta. `prepare_f1.py` owns that check. Manifest `tooling` contains `files` (absolute pinned file records), `links` (absolute path, resolution, link text and existence), `trees` (exact external member lists), and `aliases` (copied-root-relative alias and fixed external resolution). `files` contains all copied files, excluding the self-referential `.gate/manifest.json`; each row binds path, SHA-256, byte count and mode. The root hash covers the entire canonical manifest excluding only `input_root_sha256`; when present, the owner’s `.gate/manifest.json` must be canonically identical to the controller’s run manifest. Surplus copied code and changed external tree membership are blocking. Full POSIX BuildIdentity ordering and Java runtime version are recorded separately.

`controller.py preflight-freeze --run-id NAME` freezes the tiny idle-child witness, predicates, verifier and tools. `controller.py preflight --run runs/NAME` may then create exactly one uniquely named transient user service. This checks effective CPU quota 400%, memory high 5GiB, memory maximum 6GiB, swap 0, tasks 512 and observed task affinity 0..3. It changes no active unit or global controller. Affinity is observed placement, not security confinement. Failed preflight runs remain immutable; repairs require another run ID and manifest. Cleanup uses unit-bound Description/root and InvocationID, unit-scoped SIGTERM and event-driven `cgroup.events` reads, followed by unit stop. Missing explicit `populated=0`, surviving identities, or cleanup uncertainty blocks the run even if the unit disappeared.

`controller.py stack-readiness --run runs/NAME --schedule-release RELEASE.json` starts only the fresh registered copied stack. The release must contain `status: SCHEDULE_RELEASED`, the exact `installation_root_sha256`, `other_performance_work_finished: true`, and `containment_preflight_run` naming a private run whose PASS evidence matches the current verifier and containment inputs. One supervisor, PostgreSQL, parser proxy/context control, Spring, all helpers and workers inherit the same transient service limits. The controller remains outside. Readiness requires the exact proxy loaded hashes, context readiness, live exact process incarnations, Spring's document POSIX lock and a successful authorized documents endpoint. Every SQL operation including bootstrap/readiness uses the copied SQLeanParser proxy. PostgreSQL and Spring budgets match the experiment. The default worker launcher is unchanged.

`controller.py stack --run runs/NAME --runtime-registration RUNTIME.json --schedule-release RELEASE.json` additionally invokes a frozen external load driver. The runtime registration must contain `status: FROZEN_RUNTIME_INPUTS`, `installation_root_sha256`, `prerequisites` with `finite_semantics`, `comparator_negative_cases`, and `p1_regressions` all `PASS`, a complete `files: [{path, sha256}]` absolute-path inventory, and `driver` equal to one inventory row inside this gate. The release must bind `runtime_registration_sha256`. The driver receives `--root COPY --output RUN/driver-report.json`; it must report `status: PASS` and the exact installation root. These prerequisites are bindings to the parent runtime closure, not a substitute for its independently registered verifiers and evidence.

`http_driver.py` constructs the original synthetic accepted 500-node document through real HTTP, checks its SOURCE roundtrip, then materializes all 1100 exact per-start requests before the first warmup. It preserves every attempted request/reply and timing, including errors. The request manifest binds installed source root, fixture hash, route, exact authorized IDs, bytes and hashes. It performs 100 warmups then 1000 serial distinct validation edits, with strict nearest-rank p95 below 300ms and zero errors; failures stop and remain recorded. The controller independently enforces whole-stack peak memory at most 5GiB. Neither one run nor an average selects F1: the parent must check every run in the three preregistered alternating pairs and all semantic/tradeoff gates. Accepted timings exclude build/copy and diagnostic instrumentation; equal cgroup observation runs in both variants.

The harness emits finite sampled ownership and resource evidence. Linux, hardware, systemd, SHA-256, pinned runtimes and unlisted system-library behavior remain trusted. It does not claim continuous observation, universal nonescape, Java semantic equivalence, solver performance or production acceptance. `TESTED_SCREEN_ONLY` remains the boundary; the actual pinned 4vCPU/8GiB host acceptance is OPEN. `test_harness.py` checks authoring boundaries without launching services, SQL, Java workloads or timings.
